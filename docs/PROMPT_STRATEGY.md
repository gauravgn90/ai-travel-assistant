# Prompt and context strategy

Every rule in the system prompt exists to prevent a specific failure. This document pairs each one
with the failure it addresses, so the prompt can be changed later without re-deriving why it says
what it says.

The prompt lives in [`src/lib/agent/prompts.ts`](../src/lib/agent/prompts.ts).

---

## Shape of a turn

```
SystemMessage      policy: sources of truth, tool rules, honesty rules, answer format
HumanMessage       ─┐
AIMessage           │ prior turns, verbatim, most recent 12 messages
HumanMessage       ─┘
HumanMessage       context block: preferences + KNOWLEDGE BASE + SOURCES, then the question
  ↓
AIMessage          may contain tool calls
ToolMessage ×N     tool results, one per call
HumanMessage       (only on partial failure) TOOL FAILURES note
  ↓
AIMessage          the answer
```

Three deliberate choices in that layout:

**Retrieved passages go in a human message, not the system prompt.** The system prompt is stable
policy; the context block changes every turn. Keeping them separate means the policy can be cached
and the block can be discarded once the turn ends, instead of accumulating stale passages across a
long conversation.

**The context block precedes the question in the same message.** The model sees the evidence before
the request, which reads as "here is what you know, now answer this" rather than "answer this, and
by the way here is some text".

**Failures get restated after the tool results.** The raw `ToolMessage` is already in the
transcript, but a failed call sitting among several successful ones is easy to skim past. A short
`TOOL FAILURES` note immediately before generation keeps the gap salient.

## The system prompt, rule by rule

### Three sources of truth

> You have exactly three sources, and you must keep them visibly separate.

This is the prompt's central move. The brief asks the assistant to *"distinguish knowledge-base
facts, MCP-provided current information, and recommendations generated by the LLM"*, and the only
reliable way to get that is to name the three categories up front and assign each one a distinct
obligation.

| Source | Obligation | Failure it prevents |
| --- | --- | --- |
| Knowledge base | Cite `[S1]` inline | Destination facts asserted from model memory, uncheckable by the reader |
| Live tools | Attribute in prose ("the forecast shows…") | A temperature or exchange rate invented because it sounded plausible |
| Own planning | Phrase as a suggestion | The model's pacing opinion read as a fact from the guides |

The third category matters more than it looks. Without explicit permission to plan, models either
refuse to sequence an itinerary (everything must be cited, and no source states the order) or they
silently attach a citation to their own recommendation. Naming it as a legitimate third category
with its own phrasing requirement resolves both.

### Tool policy, stated in both directions

> Call a tool only for live information. Questions about what to see, where to stay, how to get
> around or what to eat are answered from the knowledge base, never from a tool.

The brief requires that *"MCP should not be used to answer destination questions already covered by
the knowledge base"*. A rule stated only positively ("call tools for weather") leaves the converse
ambiguous, and models with a web-capable tool in scope will reach for it. Stating the converse
explicitly, with examples of the categories it covers, closes that.

Supporting rules:

- **"Resolve relative dates yourself against today's date before calling."** Today's date is in the
  prompt. Without this, "next week" is passed to the tool verbatim and the call fails on a
  validation error.
- **"Do not call the same tool twice with the same arguments."** Prevents a loop where the model
  re-fetches a forecast it already has, burning iterations against `MAX_TOOL_ITERATIONS`.
- **"If a tool returns an error, say which information is missing and answer the rest."** The
  brief's requirement to *"handle unavailable tools or failed results without fabricating an
  answer"*. The important half is *answer the rest* — a failed currency lookup should not cost the
  user their itinerary.

### Honesty

> If the knowledge base does not cover what was asked, say so in one sentence and state what it
> does cover.

Paired with the retrieval gap detection described in the README. When the best cosine falls below
the coverage floor, the context block is replaced with an explicit instruction not to answer
destination facts from memory. Belt and braces: the retrieval layer decides coverage
mechanically, and the prompt states the consequence.

> Never attach a citation marker to a statement that the cited passage does not support.

Models will happily decorate a sentence with `[S2]` because a marker appears nearby in the context.
Stating the prohibition directly measurably reduces it.

> Prefer "the guides do not say" over a confident guess.

Gives the model an approved way to fail. Without an explicit alternative, the path of least
resistance is to answer anyway.

### Answering

Format rules are deliberately minimal — lead with the answer, short paragraphs, structure only when
the content is genuinely a list, day/morning-afternoon-evening for itineraries, name an indoor
alternative when the forecast matters. They exist because travel answers default to bullet soup
otherwise, and because the brief's central scenario needs a specific shape.

> Carry the user's stated preferences across turns without being asked again.

Backed mechanically by the preference block described below; the prompt states the expectation so
the model actually uses what it is given.

## The context block

Assembled per turn by `buildContextBlock`.

### Preferences

```
# TRAVELLER PREFERENCES (carried from earlier turns)
- Budget: 60,000 INR
- Trip length: 3 days
- Travelling as a family with children
- Interests: food, culture and heritage
```

Extracted by rules from each user message — see
[`src/lib/session/preferences.ts`](../src/lib/session/preferences.ts) — and merged into the session.
Later turns supersede earlier ones per key; interests accumulate.

Rules rather than an LLM call because the facts worth pinning are stated in a small number of
predictable phrasings, and a rule pass is free, deterministic, and cannot invent a constraint the
traveller never mentioned. The trade-off is recall on unusual phrasing. Since the raw transcript is
still in context, a missed rule degrades to "not pinned", not "forgotten".

The parenthetical "carried from earlier turns" matters: without it, models sometimes acknowledge
the preferences back to the user as though they had just been stated.

### Knowledge base

```
# KNOWLEDGE BASE
Use only these passages for destination facts. Cite them by marker.

[S1] Visit Singapore: Sample Itineraries > Three days in Singapore > Day 1
Morning: Gardens by the Bay, starting with the conservatories before the heat peaks…

---

[S2] Wikivoyage: Singapore Travel Guide > Get around > Fares
Fares are charged based on distance and mode of transport…
```

Each passage carries its marker, document title and heading path. The heading path is what lets the
model say "the guides list this under Sentosa" and what makes a mis-citation visible to a reviewer.

Chunks from the same document share one marker, so answers cite documents rather than offsets —
which is what a reader wants to click.

### Sources

A flat list mapping each marker to title, publisher and URL, so the model can name a source in prose
without being handed the URL inline in every passage.

### Gap variant

When retrieval finds nothing above the coverage floor, the whole knowledge-base section is replaced:

```
# KNOWLEDGE BASE
No passage in the knowledge base matched this question. Do not answer destination facts from
memory. Tell the user the guides do not cover it, and offer the closest topic you can help with.
You may still use tools for live information.
```

The last sentence is load-bearing. Without it, a gap on "convert 200 SGD to INR" — which correctly
scores below the floor, being a tool question rather than a corpus question — would suppress the
tool call as well.

## Degradation

When an MCP server fails to start, the system prompt says so by name:

```
These tool servers are currently unavailable: travel-currency. If a question needs one of them,
say plainly that you cannot check it right now.
```

The model can then answer the parts it can and be specific about what it could not check, rather
than either failing the whole turn or quietly guessing.

## What was tried and rejected

**Few-shot examples of good answers.** Improved format adherence slightly, cost several hundred
tokens per turn, and made answers converge on the shape of the examples regardless of the question.
Explicit format rules got most of the benefit for a fraction of the context.

**Asking the model to emit a structured provenance block.** Redundant: retrieval and tool results
are already tracked by the orchestrator as the turn runs, and are strictly more reliable than the
model's own account of what it used.

**A separate LLM call to extract preferences.** Doubled the per-turn cost, added latency to every
turn, and occasionally invented constraints. Rules do the job for the phrasings that actually occur.

**A "you are a friendly travel expert" persona preamble.** Consumed tokens and changed nothing
measurable about grounding, citation accuracy or tool selection.
